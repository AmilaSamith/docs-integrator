# How to Add a New Connector

This is the checklist for adding a new connector to the catalog
(`en/docs/connectors/catalog/`, ~165 entries today). Unlike the rest of
this repo, `en/sidebars.ts` on this branch is **hand-maintained, not
autogenerated** — its own header comment explains why — so a new
connector needs a few manual steps the general
[CONTRIBUTING.md](CONTRIBUTING.md) conventions don't cover. No `slug:`
frontmatter and no `_category_.json` are needed anywhere under
`en/docs/connectors/` — don't add them here even though CONTRIBUTING.md
says to elsewhere.

## 1. Create the folder and its pages

`en/docs/connectors/catalog/<area>/<package-id>/`, where `<area>` is the
existing category folder it belongs in (`communication/`, `database/`,
`storage-file/`, etc. — see the folder list, or `catalog/index.mdx`'s
`category` values, for the current set) and `<package-id>` matches the
Ballerina package name (e.g. `twilio`, `aws.sqs`, `hubspot.crm.contacts`).

Every connector has:

| File | Required | Notes |
|---|---|---|
| An overview page | Always | Name it whatever fits (`overview.md`, `connector-overview.md`, `<id>.md` — all three conventions already coexist; its filename never reaches the sidebar, see step 3, so there's no fixed convention to follow here) |
| `setup-guide.md` | Only if the connector needs external configuration (API keys, OAuth, endpoints) | Built-in/protocol connectors (HTTP, TCP, FTP, ...) skip this — nothing to configure |
| `actions.md` or `action-reference.md` | If the connector has actions | Either filename is fine |
| `triggers.md` or `trigger-reference.md` | Only if the connector supports triggers | Most connectors are action-only — see `overview.md`'s Actions-vs-Triggers table |
| `example.md` | Always | |

## 2. Required frontmatter — exact titles, no variants

Every one of the four sub-page types must use **exactly** this `title:`,
with no plural, no "Reference" suffix, no connector name prepended:

```yaml
---
connector: true
connector_name: "<package-id>"
title: "Setup Guide"   # or "Actions" / "Triggers" / "Example"
---
```

This isn't just a style preference — the sidebar swizzle
(`en/src/theme/DocSidebarItem/Link/index.tsx`'s `CONNECTOR_SUBPAGE_LABELS`)
matches these exact strings to decide which icon to render next to each
sub-page, since the sidebar label falls back to this `title:` field (no
`sidebar_label` is set on these pages). A connector that used "Examples"
or "Action Reference" instead silently lost its icon — this was a real
bug, fixed across all ~165 connectors, and this exact-title rule is what
keeps a future connector from reintroducing it.

The overview page's title can be anything — its sidebar label comes from
the hardcoded `label:` in the `sidebars.ts` category entry (step 3), not
from the doc's own frontmatter.

## 3. Add the `sidebars.ts` entry

Find the connector's `<area>` category in `en/sidebars.ts` (alphabetical
by connector label within each area) and insert:

```ts
{
  type: 'category',
  label: 'Your Connector Name',
  link: { type: 'doc', id: 'catalog/<area>/<package-id>/<overview-filename-without-.md>' },
  items: [
    'catalog/<area>/<package-id>/setup-guide',       // omit if no setup guide
    'catalog/<area>/<package-id>/action-reference',  // or actions, matching step 1
    'catalog/<area>/<package-id>/trigger-reference', // omit if no triggers
    'catalog/<area>/<package-id>/example',
  ],
},
```

`label` is what actually renders in the sidebar and the collapsed icon
rail's tooltip — get the capitalization right (e.g. `AI`, `gRPC`, `AWS
SQS`), it isn't derived from anything else.

## 4. Add the catalog card in `catalog/index.mdx`

Add one entry to the `connectors` array:

```ts
{
  name: 'Your Connector Name',
  description: 'One or two sentences — shown on the card, truncated past ~120 characters with a "Show more" toggle.',
  operations: 12, // count of distinct actions/triggers
  auth: 'API Key', // or 'OAuth2', 'Basic Auth', 'None', etc.
  link: '/<area>/<package-id>/<overview-filename-without-.md>',
  category: 'Communication', // must match one of the existing `categories`/tint keys — see CATEGORY_TINTS in components/ConnectorCatalog/index.tsx
  icon: 'https://...',   // see below
  vendor: 'Twilio',      // see below
  version: '1.2.0',      // see below
},
```

If `vendor` introduces a name not already in the file's `vendors` array,
add it there too (kept in sync manually, same file).

**Sourcing `icon`/`vendor`/`version` from Ballerina Central** — don't
guess these:

```bash
curl -s https://api.central.ballerina.io/2.0/registry/packages/ballerinax/<package-id> # version list
curl -s https://api.central.ballerina.io/2.0/registry/packages/ballerinax/<package-id>/<version> # full metadata: icon, keywords, etc.
```

The response's `icon` field is the real hosted icon URL — use it
directly rather than hosting a local copy. Derive `vendor` from the
package's `Vendor/` keyword (see [Publish
Connector](en/docs/connectors/build-your-own/publish-connector.md) for
what these keywords mean) — don't infer it from the package name (e.g.
all `aws.*` packages are `Vendor/Amazon`, not "AWS"). A handful of
connectors genuinely have no icon upstream — omit the field rather than
fabricating one; the card falls back to a colored initials badge.

## 5. Verify

```bash
cd en
npm run typecheck
npx docusaurus build
```

The build fails the build on any new broken link. A handful of
broken-link warnings are pre-existing (stale cross-branch links that only
resolve in the merged production site) — if you're unsure whether one is
pre-existing, check whether it's still reported without your change.

Then spot-check in a served build: your connector's card renders in
`/catalog` with the right icon/vendor/category tags, and clicking into it
shows the sidebar scoped to just that connector (Overview, your
connector's own pages with icons next to Setup Guide/Actions/Triggers/
Example, and "Build a Connector" still visible) — see
`en/src/theme/DocRoot/Layout/Sidebar/index.tsx`'s docstring for how that
scoping works.
